# T 市綠塔：智慧建築 3D Digital Twin Demo 企劃

> 情境為虛構：假設台北 101 是 T 市的一棟綠建築改造案。外型取其「八節堆疊」的輪廓語彙，所有設備容量、用電與發電數字都是**合成數據**，不代表台北 101 的實際設計或營運。

## 1. 目標

在 GitHub Pages 上跑一個瀏覽器 3D 數位孿生 demo，讓人一眼看懂一棟「會發電、會儲能、會調度」的大樓：

- **看得到**：大樓、廣場、地下室儲能、AI 機房、停車場充電樁都有 3D 模型，可旋轉、縮放、點選。
- **看得透**：一鍵透視（X-ray），外牆變半透明，看見樓層、機房、地下室與管線。
- **看得懂能量**：太陽能、電網、儲能、AI 機房、一般大樓負載、電動車充電之間的能量流以動畫線條即時呈現（in／out、方向、粗細＝功率）。
- **能調整平衡**：使用者拉動策略參數（儲能策略、EV 充電上限、AI 工作負載可延後比例、契約容量），系統自動重新調度，即時看到電費、碳排、自發自用率、尖峰削減的變化。
- **能看細節**：點任一設備看即時數值、24 小時曲線與狀態。

3D 素材全部走「Gemini 生成 mockup → TRELLIS.2 轉 3D」的流程，延續 yukimura 人物 2D 轉 3D 的經驗，驗證它用在建築／設備場景的可行性。

## 2. 虛構建築設定

| 系統 | 設定（合成） | 位置 |
| --- | --- | --- |
| 外牆光電（BIPV） | 南、東兩面改為新一代半透明光電玻璃，各約 27,000 m²、效率 18%（假設）；垂直安裝，晴天實際峰值約 2.3 MW、日發電約 19 MWh | 南、東立面 |
| 一般大樓負載 | 辦公、空調、電梯、照明；平日尖峰約 8.5 MW、夜間約 3.2 MW | 全棟 |
| AI 機房 | 2 MW IT 負載、PUE 1.25；其中 30% 為可延後的訓練工作 | 地下 B3（與儲能同層） |
| 儲能系統（BESS） | 5 MW／10 MWh 鋰電，液冷貨櫃式機櫃 | 地下室 |
| 電動車充電 | 120 支 11 kW 交流 + 8 支 120 kW 直流，可排程 | 地下停車場 |
| 廢熱回收 | AI 機房冷卻水廢熱供熱水／除濕（示意） | 機房 → 熱水系統 |
| 電網 | 台電時間電價（尖峰／半尖峰／離峰，示意費率）、契約容量、需量反應事件 | 受電室 |

數字以「看起來合理、能說故事」為準，集中列在 [`src/sim.ts`](../src/sim.ts) 的 `ASSUMPTIONS`，方便日後替換為真實數據或 API。

**第一版模擬得到的重要事實**：就算兩整面都換成光電玻璃，垂直外牆在晴天也只供應全棟約一成用電（晴天平日約 9.9%）。所以這棟樓的 EMS 價值主要不在「自給自足」，而在**削峰、移峰與需量反應**：儲能把尖峰電價時段的購電壓下來，AI 訓練與 EV 充電移到便宜或光電多的時段。Demo 的敘事要照這個事實來說，避免誇大光電。

## 3. 系統架構

```
Gemini (Nano Banana Pro) ──► mockup 圖（四立面、設備、場景）
        │ 去背（key_views）
        ▼
TRELLIS.2 on Modal H100 ──► GLB（大樓用四視圖拼接、設備用單圖）
        │ Draco + WebP 壓縮
        ▼
web/（Vite + TypeScript + three.js）──► GitHub Pages
   ├─ 場景：大樓 GLB + 程序化內部（樓板、機房、地下室、停車層）+ 設備 GLB
   ├─ 能量流：沿路徑移動的粒子／發光管線，粗細與速度＝功率
   ├─ 合成數據產生器：日照、天氣、負載、EV 到站、AI 任務（可重現的 seed）
   ├─ EMS 調度器：規則式（之後可換成最佳化）每 15 分鐘一步
   └─ UI：時間軸、情境選單、策略滑桿、KPI、設備詳情面板
```

全部在前端執行，不需要後端，也不在前端放任何金鑰；Gemini 與 Modal 只在離線製作素材時使用。

## 4. 合成數據與自動能源系統

**輸入（每 15 分鐘，共 96 步／天）**
- 日照：依季節、時間、立面方位（南／東）計算垂直面日射，再乘上雲量（晴天、多雲、颱風日三種）。
- 大樓負載：辦公作息曲線 + 溫度相關空調負載 + 隨機擾動。
- AI 機房：固定推論負載 + 可移動的訓練批次。
- EV：依上下班時間產生到站／離站事件與需求電量。
- 電價與碳排係數：時間電價表；電網碳排係數取約 0.49 kgCO₂e/kWh（示意值）。

**調度規則（第一版，規則式）**
1. 太陽能優先自用（大樓 → AI 機房 → EV）。
2. 有餘電先充儲能，滿了再降低購電或回送電網。
3. 尖峰時段儲能放電削峰，守住契約容量。
4. EV 依離站時間排序，智慧延後到離峰或太陽能時段。
5. AI 訓練工作在太陽能多或離峰時跑，尖峰或需量反應事件時暫停。
6. 需量反應事件：一鍵觸發，看系統如何在 1 小時內降載。

**輸出 KPI**：自發自用率、再生能源比例、尖峰需量、電費、碳排、儲能 SoC、EV 滿足率、AI 工作延遲時數。每個 KPI 都能和「沒有 EMS」的基準情境並排比較。

## 5. 3D 素材清單與做法

| 素材 | 生成方式 | TRELLIS.2 做法 |
| --- | --- | --- |
| 綠塔本體 | Gemini 四立面（南、東有光電玻璃，北、西為一般玻璃） | 四視圖拼接，1536 cascade |
| 儲能機櫃 | Gemini 單張 3/4 視角產品圖 | 單圖 |
| 電動車充電樁 | 同上 | 單圖 |
| AI 機房機櫃組 | 同上 | 單圖 |
| 光電玻璃模組、冷卻水塔、受電設備、車輛 | 第二批 | 單圖 |
| 廣場與周邊街廓 | Gemini 鳥瞰概念圖作為設計參考 | 不轉 3D，以程序化地面與簡化方塊建築呈現 |
| 內部樓層、管線、能量路徑 | 不用生成 | three.js 程序化幾何（需要準確對位，生成模型做不到） |

### 從 yukimura 帶過來的經驗

- **多視角比單張好**：單張圖時背面是「猜」的；給正、背、側面圖後，按體素位置分區引導，背面會「照圖」長。大樓的四個立面不同（兩面光電、兩面一般玻璃），正好用四視圖拼接。各視圖必須同比例、同構圖，所以後三張都以南立面為參考圖來畫。
- **Nano Banana Pro 最忠於參考圖**，適合畫一致的多視圖；灰底、正交、平光的提示寫法沿用。
- **去背**：灰底從邊框連通去背，給 TRELLIS 乾淨的 alpha，並跳過另需授權的 RMBG。
- **TRELLIS 的限制**：細節會「融化」、直線不夠直、邊緣有凹凸；加面數不會自動變好。建築需要直線與重複的帷幕格，這是本案最大的風險（見第 7 節）。
- **網頁用壓縮**：Draco 幾何 + WebP 貼圖，可把 70 MB 降到約 8 MB。
- **seed 只影響看不到的地方**：重要素材跑 2–4 個 seed 挑最好的。
- **Tripo 品質更好**：一次生成就勝過 TRELLIS.2 加九輪精修，三視圖不加價。本案以 TRELLIS 為主（使用者要求、開源），若大樓品質不足，Tripo 是備案。

## 7. 風險與對策

| 風險 | 對策 |
| --- | --- |
| 大樓細長（高寬比約 1:8），TRELLIS 體素是立方體，水平解析度只剩約 1/8 | 先試整棟；不夠細就分段生成（每兩節一段）再堆疊，或只用 TRELLIS 做外觀、內部用程序化幾何 |
| 帷幕格線、直角被生成「融化」 | X-ray 模式改用程序化外殼；必要時在 three.js 用貼圖或 shader 補帷幕格線；或改用 Tripo |
| 四視圖不一致導致接縫 | 都以南立面為參考圖生成；檢查高度與節數一致再送 TRELLIS |
| GLB 太大、手機跑不動 | Draco + WebP、控制面數；設備用實例化重複放置 |
| 合成數據被誤認為真實 | 介面與文件明確標示「虛構情境／合成數據」 |

## 8. 成本估計

- Gemini 3 Pro Image：每張約 0.14 美元，第一批約 8 張、全案約 20–30 張。
- TRELLIS.2：Modal H100 每次約 5 分鐘，重用 yukimura 已驗證的映像與權重快取，全案約 10–20 次。

## 9. 驗收

- GitHub Pages 開得起來，桌機與手機尺寸都能操作。
- 至少一棟大樓與三種設備是 TRELLIS 生成的模型。
- 24 小時合成數據自動播放，能量流方向與數值一致（能量守恆：來源總和＝用量總和＋儲能變化，每一步誤差 < 0.1%）。
- 調整任一策略參數，KPI 與能量流即時改變，並可與基準情境對照。
